# PYPY Grid — Administrator Guide This document provides comprehensive administrative and operational procedures for managing the PYPY Grid Smart-Grid Cybersecurity SaaS Platform in a production environment. --- ## 1. System Architecture PYPY Grid is structured as a containerized, decoupled microservices architecture designed to serve high-concurrency simulation and analytics tasks. The platform consists of the following components: - **FastAPI Gateway**: Serves the REST API, manages user authentication, issues JWT claims, and enforces multi-tenant boundaries. - **Vite React Frontend Dashboard**: Serves the user interface, telemetry panels, setup wizard, and admin portal. - **Celery Task Worker**: Handles long-running numerical simulations, Newton-Raphson solvers, and AI assistant prompt indexing. - **PostgreSQL Database**: Stores user accounts, tenant records, subscription histories, experiment summaries, and audit logs. - **Redis Cache & Message Broker**: Acts as the Celery broker, holds user sessions, and caches frequently queried analytics tables. - **Mosquitto MQTT Broker**: Facilitates real-time message passing of telemetry data from the digital twin simulation engine to the dashboard client. - **NGINX Reverse Proxy**: Terminal SSL connections, enforces rate limits, secures headers, and proxies requests to the appropriate container gateways. --- ## 2. Admin Portal Configuration Super-administrators and authorized operators can access the **Administration** panel from the main workspace sidebar. The administration module contains two main views: 1. **System Analytics**: Real-time business intelligence metrics including Daily Active Users (DAU), Monthly Active Users (MAU), monthly recurring revenue, subscription plans distribution, trial conversion rates, and simulation execution stats. 2. **Tenant Controls**: The directory of registered organizations and research labs. Admin users can override tenant subscription states, manually upgrade accounts to Academic Premium or Research Lab tiers, or downgrade delinquent accounts back to the Free tier. --- ## 3. Managing Users & Tenants Every user in the system belongs to a Tenant (multi-tenant architecture). A tenant represents a university department, a private research laboratory, or a corporate evaluation team. ### Onboarding New Research Labs When a new organization registers, a Tenant record is created, and the primary admin account is provisioned. As a system administrator, you can check active trials in the database: ```sql SELECT id, name, plan_tier, created_at FROM tenants WHERE plan_tier = 'free'; ``` To manually upgrade a tenant to Academic Premium: ```sql UPDATE tenants SET plan_tier = 'academic_premium' WHERE subdomain = 'utm-cyber'; ``` This automatically updates their subscription status and triggers the background task to unlock historical experiments. --- ## 4. Database Administration & Backup The Postgres database holds critical user metadata and experiment logs. Keeping it backed up is vital for disaster recovery. ### Backup Schedule Backups are automated via the `scripts/backup.sh` script, which should be scheduled as a daily cron job at 02:00 UTC: ```bash 0 2 * * * /home/demie/.gemini/antigravity/scratch/smart-grid-cybersecurity/scripts/backup.sh >> /var/log/pypygrid/backup.log 2>&1 ``` ### Manual Backup Execution ```bash ./scripts/backup.sh ``` This produces a compressed SQL file under `./backups/` containing all tables, schema definitions, and sequence indices. ### Disaster Recovery Restore In the event of database corruption or migration: ```bash # Extract the backup tar -xzf backups/pypy_backup_XXXXXXXX.tar.gz -C backups/restore/ # Drop and recreate database docker compose -f docker-compose.prod.yml exec -T postgres dropdb -U pypy_admin pypy_saas docker compose -f docker-compose.prod.yml exec -T postgres createdb -U pypy_admin pypy_saas # Restore tables docker compose -f docker-compose.prod.yml exec -T postgres psql -U pypy_admin -d pypy_saas -f backups/restore/pypy_db_backup.sql ``` --- ## 5. Monitoring & Alerting Monitoring is handled natively using Prometheus metrics endpoints exported by the FastAPI gateway and system containers, visualized in Grafana. - **Port 9090**: Prometheus Server - **Port 3000**: Grafana Dashboard Key metrics to monitor: - `pypy_api_latency_seconds`: Average response time of gateway requests. Must be < 150ms. - `pypy_simulation_runtime_seconds`: Average execution time of the power flow solvers. - `celery_queue_length`: Length of simulation tasks queue. A queue > 5 indicates worker overload. - `mqtt_throughput_messages_second`: Telemetry flow rate. --- ## 6. Troubleshooting Common Issues ### Issue: Simulation Queue Bottleneck If simulations are stuck in the "PENDING" or "QUEUEING" state: 1. Check Celery worker container logs: ```bash docker compose -f docker-compose.prod.yml logs -f celery_worker ``` 2. Verify Redis is reachable and not out of memory: ```bash docker compose -f docker-compose.prod.yml exec redis redis-cli ping ``` 3. Scale up Celery workers if queue length is persistently high: ```bash docker compose -f docker-compose.prod.yml up -d --scale celery_worker=4 ``` For support queries, consult the internal admin
