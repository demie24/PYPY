# PYPY — Project Story and Presentation Guide

**Version 1.0 · 10 September 2026 · Audited working tree at HEAD `5f00008a8ece9a13aaaa37d1ce5c91668b7e7b9e`**

Use this guide to explain the project conversationally. Technical details and source references are in the [complete manual](PYPY_COMPLETE_USER_AND_TECHNICAL_MANUAL.md); the [audit report](PYPY_DOCUMENTATION_AUDIT_REPORT.md) records limitations. Do not memorise every sentence. Remember the sequence: **measure → detect → check → decide → respond → verify**.

## 1. The problem

**Say:** “An electricity network depends on information as well as electrical equipment. The operator needs to know the voltage, the power flow and which breakers are open. If that information is changed, even a healthy grid can appear to need the wrong intervention.”

Use a simple example: a report says a bus voltage is dangerously high, but that report has been tampered with. A controller that trusts it immediately could make an unnecessary switching decision. The engineering problem is therefore not only finding suspicious data; it is deciding what to do safely.

**Show:** Live Grid. Point at a bus, a branch and a breaker. Explain that these are the simulated electrical assets, not containers or network packets.

## 2. Why conventional cybersecurity is not enough

**Say:** “A firewall can restrict who communicates, but it does not by itself tell us whether an electrical measurement makes sense. PYPY explores that additional question by checking the data against both learned patterns and a grid model.”

Do not say firewalls are useless or that PYPY replaces them. Network access control, authentication and secure communications remain necessary. The current local control path also needs substantial hardening before any production deployment.

A useful analogy is a hospital monitor: securing the cable matters, but a clinician still checks whether the reported vital signs agree with the patient and other measurements. PYPY demonstrates that second style of check using simulated electrical state.

## 3. The PYPY idea

**Say:** “I use an immune-system analogy. The grid is the body, telemetry is its vital signs, the detector watches for unusual patterns, validation checks whether the evidence is credible, and the response logic decides whether intervention is justified.”

| Analogy | Actual component | Where the analogy stops |
|---|---|---|
| Body | IEEE-39 simulated grid | It is not a living or deployed utility system |
| Vital signs | MQTT voltage/flow/breaker telemetry | Measurements are generated by simulation |
| Surveillance | Autoencoder and model services | Anomaly does not establish attacker identity |
| Diagnosis | Physics/trust/fusion | Checks share model assumptions |
| Treatment planning | Recovery proposals and orchestrator | Some rules are deterministic; not every choice is learned |
| Intervention | Simulated control and recovery | Physical equipment is not exercised here |
| Memory | Event records and research memory modules | Ordinary logs do not automatically retrain models |

The memorable phrase is: **“Detect unusual information, check its physical meaning, and verify the outcome of any response.”**

## 4. What happens during normal operation

**Say:** “The digital twin calculates the simulated grid state about once a second. MQTT distributes it. The browser displays it, while the detector, AI models and physics checks analyse it.”

Before an experiment, the autoencoder calibrates and the temporal models collect a sequence. Fusion also needs nominal reference samples. Let the system settle before showing an attack.

**Show:** Overview and Live Grid. Point at the IEEE39 label, incoming data, breaker state and solver evidence in the terminal. Explain that a green interface is useful, but timestamps and solver convergence are stronger evidence.

**Important:** The recorded nominal threat score was around 30, labelled MEDIUM. Say “This is the measured baseline,” not “A normal grid always has zero threat.” The scorer includes voltage/loading margins and recent history. PPO/DQN choosing NO_ACTION is normal when no branch needs restoration.

## 5. What happens when an attacker appears

**Say:** “For the first example, I change one reported voltage. I add 0.15 per unit to Bus_5 through the simulator's FDIA function. The change ramps in over several samples. I am altering the report, not physically turning up a generator.”

Use the explicit command in the demo script. The current form does not include FDIA magnitude fields, so its default FDIA button is not the verified trigger.

**Show:** Attack Simulation and Cyber Detection. Point at the active scenario and changed voltage. Make clear that the attack label comes from the experiment generator; it is not evidence that a model independently recognised the attack type.

## 6. How PYPY detects the problem

**Say:** “The small autoencoder tries to reconstruct the expected voltage pattern. A large reconstruction error is a candidate anomaly. The detector waits for repeated evidence before publishing an alert.”

In the rehearsal, the alert was a critical `GRID_DEVIATION` identifying Bus_5. Do not promise it will literally say FDIA. The detector's label is based on error-pattern rules.

**Then say:** “Other models examine temporal and graph patterns. Their outputs are compared with their own nominal baselines before fusion combines them.”

The four named models are LSTM, GNN, ST-GNN and PINN. Do not explain every neural-network equation unless asked. Their roles matter more in the opening demonstration than their layer counts.

## 7. How PYPY checks whether the problem is genuine

**Say:** “An unusual reading can come from an attack, a real fault or a bad sensor. PYPY also checks electrical consistency and maintains trust scores. I compare these signals rather than treating one model output as proof.”

**Show:** AI Decision, especially physics and trust evidence. Explain that KCL/KVL-related checks ask whether electrical quantities agree with the model. Trust decreases when evidence becomes inconsistent and can recover gradually.

Be precise about confidence: “This is a calculated operational confidence index.” Do not call 98% confidence “98% detection accuracy.” The latter requires a labelled evaluation dataset and a defined metric.

Also disclose the mode: “This demo uses experiment-aware scoring. The scorer has access to known attack context. The independent reconstruction alert is separate evidence.”

## 8. How PYPY decides what to do

**Say:** “Detection and action are separate. A model or recovery module can propose a command, but the orchestrator can reject it. The important question is whether the action meets the implemented safety and decision conditions.”

During the FDIA rehearsal, proposed isolation actions were rejected. This is a strong explanation opportunity: the system is not required to make the most dramatic response. A rejection with a clear reason is an observable decision outcome.

**Show:** The latest orchestrator decision and, if needed, raw `grid/orchestrator/events`. The full reason is more useful than a green/red badge.

Avoid “Every command is impossible to bypass.” Direct operator controls follow a separate path, and the current deployment is a local research platform.

## 9. How PYPY responds

**Say:** “In this first experiment, the response was to flag the abnormal report and reject proposed switching. No breaker opened. I now stop the injected signal, and the reported voltage returns to its baseline.”

This is intentionally modest and exact. Stopping the attack is an operator action; it is not AI repair. Do not imply that a hidden autonomous routine removed an attacker from a real network.

The physical recovery example comes next and uses a different trigger. Introduce it explicitly: “Now I will demonstrate the restoration path separately.”

## 10. How the grid recovers

**Say:** “For this second example, I open one simulated branch, L_line_0, and stop the attack. The policies evaluate restoration. They agree on a close intent, the sandbox checks the predicted result, the orchestrator approves, and the next telemetry confirms that the breaker closed.”

This sequence was observed in the fresh rehearsal. Point at the OPEN state, the policy source, explicit safe/finite/converged sandbox fields, approval, forwarded control and later CLOSED state. The branch ID matters more than the visual colour.

If the UI policy cards say “Unavailable,” explain the existing field-mapping gap and show the raw policy message. Do not disguise the mismatch or claim it means policy inference is absent.

PPO/DQN use a compatibility adapter for IEEE-39. Say that plainly if describing training: the active code explicitly marks the policies as not retrained on IEEE-39.

## 11. Why this is useful

**Say:** “The platform makes the connection between data manipulation and electrical decisions visible. It lets me run controlled experiments, inspect why a response was accepted or rejected, and check the resulting simulated state.”

Its value is educational and experimental: repeatable scenarios, observable message flow, model integration, physics checks and traceable controls. A useful research result includes limitations and failures, not just a successful animation.

For future deployment, the work would need stronger authentication and command authority, persistent evidence storage, independent evaluation, validated physical models, and tested hardware integration. These are future engineering tasks, not features to imply are already complete.

## 12. What I actually built

A safe project-level statement is:

> “PYPY integrates an IEEE-39 digital twin, MQTT telemetry, anomaly and AI analysis, physics/trust checks, recovery proposals, orchestration and a web control centre. I can demonstrate a detected measurement injection and a separately validated simulated breaker restoration.”

Personal contribution cannot be established from repository inspection alone. Replace “I implemented…” with a specific, truthful account based on your development history: which module you designed, which integration you completed, which experiment you ran, and which result you evaluated. Do not take personal credit for every dependency, inherited module or generated file.

### A 30-second version

“PYPY is a simulated smart-grid cybersecurity platform. It produces electrical telemetry, introduces controlled attacks, detects unusual patterns, checks physics and trust, and evaluates response proposals. My demonstration shows an FDIA detected on Bus_5 and a separate breaker restoration that passes policy consensus, sandbox checks and orchestrator approval. The grid is simulated, and I keep the model and deployment limitations explicit.”

### A five-slide narrative

1. **Problem:** false information can cause unsafe electrical decisions.
2. **System:** simulated grid → MQTT → analysis → validation → proposed response.
3. **Detection example:** Bus_5 FDIA, actual anomaly alert and rejection evidence.
4. **Recovery example:** L_line_0 OPEN → sandbox → approval → CLOSED.
5. **Contribution and limits:** integrated observable platform; simulation, model provenance, UI and evaluation caveats.

Avoid “100% secure,” “all attacks detected,” “every model is autonomous,” “real grid data,” and “FDIA automatically caused and repaired a physical outage.” None is established by this audit.
